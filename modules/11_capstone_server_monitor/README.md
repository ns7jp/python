## 2. 🖥 サーバーエンジニアにとってなぜ重要か

サーバー構築・運用の仕事の中でも、「監視(モニタリング)」は
特に重要な業務の1つです。

- **障害の早期発見**: サーバーが落ちていることに誰も気づかないまま
  何時間も経ってしまう、というのは運用の現場で絶対に避けたい事態
  です。定期的に自動でチェックし、異常があればすぐに知らせる
  仕組みが欠かせません。
- **「一時的な不調」と「本当の障害」の見分け**: ネットワークは
  一瞬だけ不安定になることもあります。1回失敗しただけで大騒ぎ
  していては誤報(誤ったアラート)だらけになってしまいます。この
  章で作る「連続失敗回数がしきい値を超えたらアラート」という
  仕組みは、実際のDatadogやMackerel、Zabbixといった監視ツールでも
  採用されている、とても実践的な考え方です。
- **複数サーバーの一括管理**: 実務では1台どころか、数十台・数百台
  のサーバーを人手で1台ずつ確認するのは現実的ではありません。
  設定ファイルにサーバー一覧を書いておき、プログラムでまとめて
  チェックする、というこの章の設計は、実際の監視ツールや
  ヘルスチェックスクリプトの基本形そのものです。
- **ログとして記録を残す**: 「いつ、どのサーバーが、どんな状態
  だったか」を記録しておくことで、障害が起きたときに「いつから
  おかしくなっていたのか」を後から調査できます。

この章を終えたときには、「未経験だけど、簡単な監視ツールなら
自分で作って動かせる」という、インフラエンジニアとして胸を張れる
実績が1つ増えているはずです。

## 3. 📖 解説

### 3.1 全体の設計(データの流れ)

この章の`monitor.py`は、次のようなデータの流れで動きます。

```
sample_config.json
      │  load_config()
      ▼
  config(dict)  ← "targets"のリストと"alert_threshold_consecutive_failures"
      │  run_monitor_cycle()
      ▼
  results(list[dict])  ← 各targetのport_ok / http_ok / healthy
      │  log_cycle_result()          │  update_failure_counts()
      ▼                              ▼
  ログファイルへ記録           failure_counts(dict)  ← 連続失敗回数
                                      │  get_alerts()
                                      ▼
                                アラート対象のリスト
```

このように、「設定を読む」「チェックする」「記録する」
「カウントする」「判定する」という役割ごとに関数を分けておくのは、
04章で学んだ「関数分割」の考え方です。1つの関数が1つの仕事だけを
担当することで、テストしやすく、後から読み返しやすいコードに
なります。

### 3.2 監視対象1つぶんのチェック(`check_target`)

設定ファイルの`targets`には、次のような監視対象が並んでいます。

```json
{"name": "web-01", "host": "127.0.0.1", "port": 8080, "http_url": null}
```

1つの監視対象に対して、この章では2種類のチェックを行います。

- **ポートチェック(`check_target_port`)**: 08章で学んだ
  `socket.create_connection`を使い、指定したhost:portにTCP接続
  できるかどうかを調べます。SSHサーバーやWebサーバーが
  「そもそも起動しているか」を確認する、最も基本的な方法です。
- **HTTPチェック(`check_target_http`)**: `http_url`が設定されて
  いる場合だけ、その URL にHTTP GETリクエストを送り、ステータス
  コードが200番台(200, 201, 204など)かどうかを確認します。
  `http_url`が`None`や空文字列の場合は「HTTPチェックはしない
  対象」とみなし、`None`を返します。

そして`check_target`関数は、この2つの結果を組み合わせて、
「total(総合)として健全(healthy)かどうか」を判定します。

- ポートが開いていない(`port_ok`が`False`)なら、無条件で不健全
- ポートは開いているが、HTTPチェックが明確に失敗している
  (`http_ok`が`False`)なら、不健全
- ポートが開いていて、HTTPチェックが成功(`True`)またはそもそも
  対象外(`None`)なら、健全

### 3.3 依存性注入によるHTTPチェックのテスト(復習: 08章)

`check_target_http`は、`http_get`という引数を受け取ります。これは
08章で学んだ「依存性注入」の考え方です。

```python
def check_target_http(http_url, http_get=None):
    getter = http_get if http_get is not None else requests.get
    ...
```

本番のCLI実行では`http_get`を渡さないので、実際に`requests.get`が
使われます。しかしテストのときには、次のような「本物そっくりの
ダミー関数」を`http_get`引数として渡すことで、外部への通信を
一切発生させずに動作を確認できます。

```python
class FakeResponse:
    def __init__(self, status_code):
        self.status_code = status_code

def fake_get(url):
    return FakeResponse(200)

check_target_http("http://example.com", http_get=fake_get)  # -> True
```

### 3.4 連続失敗回数のカウント(`update_failure_counts`)

サーバー監視では、「1回失敗しただけですぐアラート」にしてしまうと、
一時的な通信の乱れでも大量の誤報が飛んでしまいます。そこで、
この章では「何回連続で失敗したか」を辞書(`{対象名: 連続失敗回数}`)
で管理します。

- そのサイクルで`healthy`が`False`だった対象は、カウントを+1する
- そのサイクルで`healthy`が`True`だった対象は、カウントを0に
  リセットする(1回でも成功したら「連続」は途切れたとみなす)

この「辞書を受け取り、新しい辞書を作って返す(元の辞書は書き換え
ない)」という設計は、03章で学んだ「ミュータブル(書き換え可能)な
データを不用意に書き換えない」という安全なプログラミングの
考え方の実践です。

### 3.5 アラート判定(`get_alerts`)としきい値

`sample_config.json`には`"alert_threshold_consecutive_failures": 3`
という設定があります。これは「3回連続で失敗したらアラートを
出す」という意味です。`get_alerts`関数は、`failure_counts`の中から
このしきい値以上に達している対象名だけを取り出します。

### 3.6 ロギングによる記録(復習: 06章)

`log_cycle_result`関数は、06章で学んだ`logging`モジュールを使い、
各対象のチェック結果を記録します。

- `healthy`が`True`のとき → `logger.info(...)`(通常の記録)
- `healthy`が`False`のとき → `logger.warning(...)`(注意が必要な記録)

06章で作った`setup_logger`関数(`FileHandler`と`Formatter`を
設定してロガーを組み立てる関数)をそのまま流用してよい、という
設計になっています。実際、この章の`__main__`ブロックや
`examples/example.py`では、06章と同じ考え方でロガーを組み立てて
います。

## 4. 💻 サンプルコードの説明

`examples/example.py`では、この章の集大成としての一連の流れを、
実際に動かして確認できます。

1. **設定ファイルの読み込み**: `sample_config.json`をJSONとして
   読み込みます。
2. **監視対象を模したローカルサーバーの準備**: `web-01`役として
   実際にlistenする(待ち受ける)ソケットサーバーを立て、
   `app-01`役としては何も待ち受けないポート番号を用意します
   (「正常なサーバー」と「落ちているサーバー」を1台ずつ模して
   います)。
3. **監視サイクルを3回繰り返す**: `run_monitor_cycle`を3回呼び
   出し、そのたびに`log_cycle_result`でログに記録し、
   `update_failure_counts`で連続失敗回数を更新し、`get_alerts`で
   アラート対象を判定します。`app-01`は3回とも失敗し続けるため、
   3回目でしきい値(3回)に達し、アラートとして表示されます。
4. **ログファイルの中身を確認**: 記録されたログの内容を最後に
   まとめて表示し、`healthy`の状態に応じて`INFO`/`WARNING`が
   使い分けられていることを確認します。

実行方法は次の通りです。

```bash
cd /home/user/python
python3 modules/11_capstone_server_monitor/examples/example.py
```

実行すると、3回分の監視サイクルの結果と連続失敗回数の推移、
最終的なアラート対象、そしてログファイルの中身が表示されます。

(参考) `examples/example.py`は、他の章と同じく単体で読んで実行
できるように、`exercises`パッケージや`solutions`パッケージには
依存せず、必要な関数を自分自身の中に定義しています。

## 5. ✍️ 演習問題

演習は `exercises/monitor.py` の1ファイルにまとまっています。
関数の中身(TODO部分)を上から順に実装していきましょう。

### 演習1: `load_config` (難易度: ★☆☆)

- **目的**: JSON設定ファイルを読み込み、辞書として返す処理を
  実装します(05章・09章の復習)。
- **ヒント**: `open(config_path, "r", encoding="utf-8")`で
  ファイルを開き、`json.load(f)`で読み込んだ結果をそのまま
  返すだけです。

### 演習2: `check_target_port` (難易度: ★★☆)

- **目的**: `socket.create_connection`によるTCP接続確認を実装
  します(08章の`is_port_open`の復習)。
- **ヒント**: `try`節で`with socket.create_connection((host, port),
  timeout=timeout):`を使い、成功したら`True`を返します。
  `except OSError:`で`False`を返せば、`ConnectionRefusedError`や
  `socket.timeout`もまとめて捕まえられます。

### 演習3: `check_target_http` (難易度: ★★☆)

- **目的**: 依存性注入によるHTTPチェックを実装します(08章の
  `check_http_status`の応用)。
- **ヒント**: `http_url`が`None`または空文字列なら`None`を
  返します。それ以外なら`http_get`(渡されなければ
  `requests.get`)でGETリクエストを送り、`200 <= response.status_code
  < 300`かどうかを返します。`try`/`except Exception:`で通信中の
  例外をまとめて`False`に変換しましょう。

### 演習4: `check_target` (難易度: ★★☆)

- **目的**: ポートチェックとHTTPチェックの結果を組み合わせ、
  1つの監視対象の総合的な健全性を判定するロジックを実装します。
- **ヒント**: `port_ok`と`http_ok`をそれぞれ計算した後、
  `healthy = port_ok and (http_ok is not False)`のような式で
  総合判定します。

### 演習5: `run_monitor_cycle` (難易度: ★☆☆)

- **目的**: 複数の監視対象をループで処理する、この章のいちばん
  外側の処理を実装します。
- **ヒント**: `config["targets"]`をfor文でループし、各要素に
  `check_target`を適用した結果をリストにまとめて返します。

### 演習6: `update_failure_counts` (難易度: ★★☆)

- **目的**: 「連続何回失敗しているか」を辞書で管理するロジックを
  実装します。元の辞書を書き換えず、新しい辞書を返す点に注意
  しましょう。
- **ヒント**: `dict(failure_counts)`で辞書をコピーしてから、
  `healthy`が`False`なら`.get(name, 0) + 1`、`True`なら`0`を
  設定していきます。

### 演習7: `get_alerts` (難易度: ★☆☆)

- **目的**: しきい値以上の連続失敗回数を持つ対象を抽出する処理を
  実装します。
- **ヒント**: リスト内包表記
  `[name for name, count in failure_counts.items() if count >=
  threshold]`で簡潔に書けます。

### 演習8: `log_cycle_result` (難易度: ★★☆)

- **目的**: `logging`モジュールを使い、監視結果を記録する処理を
  実装します(06章の`setup_logger`と組み合わせて使うことを
  想定しています)。
- **ヒント**: `results`をループし、`healthy`が`True`なら
  `logger.info(...)`、`False`なら`logger.warning(...)`で、
  対象名やチェック結果をメッセージに含めて記録します。

## 7. 🚀 発展課題

余裕がある人は、次の課題にもチャレンジしてみましょう。

- **発展1**: `run_monitor_cycle`を1回だけでなく、`for`文や
  `while`文で複数回ループさせ、各サイクルの結果を時系列の
  リスト(`history`)に記録していく`run_monitor_loop(config,
  cycles, http_get=None)`のような関数を作ってみましょう。どの
  サイクルでどの対象が不健全だったかを後から振り返れるように
  なります。
- **発展2**: `get_alerts`でアラート対象が見つかったときは、
  `log_cycle_result`とは別に、`logger.error(...)`でひときわ
  目立つログレベルでも記録するようにしてみましょう
  (`log_alerts(logger, alerts)`のような関数を追加するのも
  よいでしょう)。
- **発展3**: `sample_config.json`と同じ内容を表す
  `sample_config.yaml`を作り、拡張子(`.json`か`.yaml`か)に
  応じて`pyyaml`(`import yaml`)と`json`のどちらで読み込むかを
  切り替える`load_config`の改良版を作ってみましょう(09章の
  内容の応用です)。
- **発展4**: 監視結果をログに記録するだけでなく、`csv`モジュールを
  使って`results`をCSVファイルに追記していく機能を追加し、
  後から表計算ソフトで開いて振り返れるようにしてみましょう
  (05章の内容の応用です)。
- **発展5**: `check_target`に「何秒でタイムアウトさせるか」を
  設定ファイルから読み込めるようにし、対象ごとに異なる
  `timeout`値を指定できるように拡張してみましょう。
