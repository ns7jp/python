## 2. 🖥 サーバーエンジニアにとってなぜ重要か

インフラエンジニアの仕事では、サーバーの構築・設定変更・自動化スクリプトの
運用など、「間違えると影響が大きい」作業をたくさん行います。たとえば:

- ポート番号の設定を1桁間違えて、サービスが外部に公開されてしまう
- ホスト名のバリデーションが甘く、不正な値が設定ファイルに紛れ込む
- ディスク使用量の計算ロジックにバグがあり、アラートが正しく飛ばない

こうした問題を**人間の目視確認だけ**に頼っていると、確認漏れや思い込みで
ミスが発生しやすくなります。特に、深夜のメンテナンス作業や、変更頻度の
高い自動化スクリプトほど、ヒューマンエラーのリスクは高まります。

そこで役立つのが **自動テスト** です。

- 一度書いたテストは、コードを変更するたびに何度でも同じ確認を
  機械的に繰り返してくれる
- テストコード自体が「このコードは何を満たすべきか」というドキュメントに
  なる
- **CI(継続的インテグレーション)** という仕組みと組み合わせることで、
  コードをGitリポジトリにpushするたびに自動でテストが実行され、
  問題があればすぐに気づける

CIの代表例として **GitHub Actions** があります。GitHub Actionsは、
リポジトリに「〇〇が起きたら△△を実行する」という設定ファイル
(ワークフローファイル)を置いておくことで、pushやプルリクエスト作成を
きっかけに自動でテストやビルドを実行してくれるサービスです。この章では
ワークフローファイルそのものは作成しませんが、「テストを書いておけば、
将来的にCIで自動実行できる」というイメージを持っておいてください。
サーバー運用の自動化ツール(Ansible用のスクリプトや社内ツールなど)を
チームで開発する場面では、こうしたCIの仕組みが「事故の少ない開発」を
支える土台になります。

## 3. 📖 解説

### 3-1. assert文の基本

`assert` は「この条件はTrueであるはず」ということをコードの中で宣言する
Pythonの構文です。

```python
assert 1 + 1 == 2          # 条件がTrueなら何も起こらない
assert 1 + 1 == 3          # 条件がFalseだと AssertionError が発生する
```

`assert` の後ろにカンマ区切りでメッセージを書くこともできます。

```python
assert 1 + 1 == 3, "1 + 1 は3にはなりません"
```

pytestのテスト関数の中では、この `assert` 文をたくさん使います。
「関数の戻り値が期待通りか」「メソッド呼び出し後の状態が正しいか」などを
`assert 実際の値 == 期待する値` という形で確認していきます。

### 3-2. pytestの実行方法

このリポジトリにはすでに `pytest` がインストールされています。以下のように
実行します。

```bash
# リポジトリのルートディレクトリで実行する
cd /home/user/python

# この章のテストだけを実行する
pytest modules/10_test_kihon/tests

# -v (verbose) を付けると、各テスト関数名と結果が1つずつ表示される
pytest modules/10_test_kihon/tests -v
```

`pytest` は、指定したディレクトリの中から

- ファイル名が `test_` で始まる(または `_test.py` で終わる)ファイル
- その中にある `test_` で始まる関数

を自動的に探し出し、順番に実行します。テスト関数の中で `assert` が
失敗すると、その関数は「FAILED」として報告され、すべての `assert` が
成功すると「PASSED」として報告されます。

失敗したときは、pytestが「どの行の、どんな値が、何を期待していたのに
一致しなかったか」を親切に表示してくれます。この情報を手がかりに、
テスト対象のコード(またはテストコード自体)のどこがおかしいのかを
調べていきます。

### 3-3. pytest.raisesで例外をテストする

「不正な入力を渡したら、ちゃんとエラー(例外)になること」を確認したい
場面はよくあります。たとえば、この章の `parse_port` 関数は、範囲外の
ポート番号を渡すと `ValueError` を送出する仕様です。「例外が発生する
こと」自体が正しい動作なので、それをテストする必要があります。

そこで使うのが `pytest.raises` です。

```python
import pytest

def test_parse_port_invalid():
    with pytest.raises(ValueError):
        parse_port("not-a-number")
```

`with pytest.raises(ValueError):` のブロックの中で実際に `ValueError`
が発生すれば、このテストは成功と判定されます。逆に、このブロックの中で
例外が発生しなかった場合(=本来エラーになるべき処理が通ってしまった
場合)は、テストは失敗と判定されます。

### 3-4. fixtureの基礎

複数のテスト関数で、同じ「準備済みのデータ」を使いたいことがよく
あります。たとえば「2件のサーバーが登録された状態のオブジェクト」を、
`get_server` のテストでも `list_names` のテストでも使いたい、
といった場合です。

このようなときに使うのが **fixture(フィクスチャ)** です。
`@pytest.fixture` というデコレーター(関数の前に付けて機能を追加する
目印のようなもの)を付けた関数を定義しておくと、テスト関数の**引数に
そのfixture関数と同じ名前を書くだけ**で、pytestが自動的にそのfixture
関数を呼び出し、戻り値を渡してくれます。

```python
import pytest

@pytest.fixture
def registry():
    """2件のサーバーが登録された状態のServerRegistryを用意するfixture"""
    reg = ServerRegistry()
    reg.add_server("web01", {"ip": "192.168.0.1"})
    reg.add_server("db01", {"ip": "192.168.0.2"})
    return reg


def test_get_server(registry):
    # 引数名を "registry" にするだけで、上のfixture関数の戻り値が渡ってくる
    assert registry.get_server("web01") == {"ip": "192.168.0.1"}


def test_list_names(registry):
    # 別のテスト関数でも、同じfixtureをもう一度使い回せる
    assert "db01" in registry.list_names()
```

fixtureを使うことで、「毎回同じ準備コードをテスト関数ごとにコピペする」
必要がなくなり、テストコードがすっきりします。またfixtureは、
テスト関数が呼ばれるたびに**新しく実行される**ので、あるテストで
データを変更しても、別のテストには影響しません。

## 5. ✍️ 演習問題

この章の演習は、**「すでに動く関数・クラスに対して、自分でテストコードを
書く」**という形式です。`exercises/` の中身はすでに完成しているので、
`tests/test_exerciseN.py` のTODO部分にassert文を書き込んでいきましょう。

### 演習1: `bytes_to_gb` のテスト(難易度: ★☆☆)

- 対象: `exercises/exercise1.py` の `bytes_to_gb(size_bytes)`
- 目的: 通常のケースと、0バイトという境界値のケースをテストできるように
  なる
- ヒント: `bytes_to_gb(1073741824)` は `1.0` になるはずです。`==` を
  使ったassert文の基本形に慣れましょう。

### 演習2: `is_valid_hostname` のテスト(難易度: ★★☆)

- 対象: `exercises/exercise2.py` の `is_valid_hostname(hostname)`
- 目的: 「有効な入力」と「無効な入力」の両方をテストし、境界値や
  異常な入力にも目を向けられるようになる
- ヒント: 無効な例は1パターンだけでなく、空文字・記号入り・先頭ハイフン
  など複数パターン用意してみましょう。1つの関数の仕様を確認するには、
  複数のケースを試すことが大切です。

### 演習3: `parse_port` のテスト・例外編(難易度: ★★☆)

- 対象: `exercises/exercise3.py` の `parse_port(value)`
- 目的: 正常系のテストに加えて、`pytest.raises` を使った例外のテストが
  書けるようになる
- ヒント: `with pytest.raises(ValueError):` のブロックの中で、
  例外が発生してほしい処理(`parse_port("abc")` など)を呼び出します。
  ファイルの先頭で `import pytest` が必要です(すでに書いてあります)。

### 演習4: `ServerRegistry` のテスト・fixture編(難易度: ★★★)

- 対象: `exercises/exercise4.py` の `ServerRegistry` クラス
- 目的: `@pytest.fixture` を使い、複数のテストで共通の準備済み
  オブジェクトを使い回せるようになる
- ヒント: まず `tests/test_exercise4.py` にコメントアウトされている
  `registry` fixtureの雛形を、実際に動くコードとして書いてみましょう。
  そのあとで、各テスト関数の引数に `registry` を受け取り、
  `registry.get_server(...)` や `registry.list_names()` の結果を
  assertで確認します。

## 6. 🔍 進め方

1. `modules/10_test_kihon/tests/test_exerciseN.py` を開き、TODOコメントの
   位置に、自分でassert文(演習3・4では `pytest.raises` や
   `@pytest.fixture` も)を書き込みます。
2. 書き終えたら、リポジトリのルートで以下を実行し、テストが通るか
   確認します。

   ```bash
   cd /home/user/python
   pytest modules/10_test_kihon/tests -v
   ```

3. すべて `PASSED` になれば成功です。もし `FAILED` になったら、
   pytestが表示するエラーメッセージ(期待した値と実際の値の違いなど)を
   読みながら、自分のテストコードを直してみましょう。
   (`exercises/` 側のコードは完成済みなので、通常は修正不要です)
4. 一通り書き終えたら `modules/10_test_kihon/solutions/test_exerciseN.py`
   を見て、模範解答と自分のテストコードを見比べてみましょう。
   まったく同じ書き方である必要はありません。違うassert文の書き方でも、
   同じ仕様をきちんと確認できていればOKです。

## 7. 🚀 発展課題

余裕がある方は、以下にもチャレンジしてみましょう。

1. **境界値のテストを増やす**: `parse_port` に対して、境界ぎりぎりの値
   (`"0"` や `"65535"` は正常、`"-1"` や `"65536"` は異常)をすべて
   テストするコードを追加してみましょう。
2. **`pytest.mark.parametrize` を調べてみる**: 同じテスト内容を、
   入力値だけ変えて何度も実行したいとき、`@pytest.mark.parametrize`
   というデコレーターを使うと1つの関数でまとめて書けます。公式ドキュメント
   や検索で調べて、`is_valid_hostname` のテストを書き直してみましょう。
3. **fixtureのscopeを調べてみる**: `@pytest.fixture` には
   `scope="function"`(デフォルト)のほかに `scope="module"` などが
   あり、fixtureをどの範囲で使い回すかを指定できます。それぞれの違いを
   調べてみましょう。
4. **CIのイメージをつかむ**: GitHub Actionsの公式ドキュメントなどを見て、
   「pushするたびにpytestを自動実行するワークフローファイル」がどんな
   見た目になるか調べてみましょう(この章では実際に作成する必要は
   ありません)。
