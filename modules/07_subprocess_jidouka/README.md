## 1. 📘 この章で学ぶこと

この章では、Pythonから外部コマンド(シェルコマンド)を安全に実行し、
その結果を扱うための基本を学びます。

- **subprocessモジュール**: Pythonから外部コマンドを実行するための
  標準ライブラリ。`subprocess.run()` を中心に使い方を学びます。
- **capture_output / text / returncode**: コマンドの標準出力を文字列として
  受け取る方法(`capture_output=True`, `text=True`)と、コマンドが
  成功したか失敗したかを表す `returncode`(終了コード)の読み方。
- **os.systemを使わない理由**: 古くからある `os.system()` には、
  「シェルインジェクション」と呼ばれるセキュリティ上の危険があることを
  理解し、代わりに `subprocess.run()` を安全な形で使う習慣を身につけます。
- **シバン行(`#!/usr/bin/env python3`)**: スクリプトファイルの1行目に
  書く特別な記述で、「このファイルを何で実行すればよいか」をOSに
  伝える仕組みです。
- **cronでの定期実行を見越したスクリプト設計**: 人間が画面を見ていなくても
  正しく動く、自動化スクリプトならではの設計の考え方を学びます。

これらは、「サーバーのヘルスチェックを定期的に行う」「複数のコマンドを
組み合わせた自動化スクリプトを作る」といった、インフラエンジニアの
実務に直結するテーマです。

## 2. 🖥 サーバーエンジニアにとってなぜ重要か

サーバー構築エンジニア(インフラエンジニア)の仕事は、「コマンドを打つこと」の
連続だと言っても過言ではありません。この章の内容は、その「コマンドを打つ」
作業を自動化するための、まさに核となる技術です。

- **監視スクリプトの基礎**: 「Webサーバーは動いているか」「ディスク容量に
  余裕はあるか」「特定のホストに到達できるか」――こういったチェックの
  多くは、既存のLinuxコマンド(`systemctl`, `df`, `ping` など)を実行し、
  その出力やreturncodeを解析することで実現します。Pythonから
  外部コマンドを呼び出せると、複数のチェックを組み合わせたり、
  結果を条件分岐させたり、通知を送ったりといった、コマンド単体では
  できない柔軟な処理ができるようになります。
- **セキュリティ意識**: `os.system()` や `shell=True` を安易に使うと、
  外部から渡された値(ユーザー入力や設定ファイルの値など)によって
  意図しないコマンドが実行されてしまう「シェルインジェクション」の
  危険があります。これは実際の障害・セキュリティ事故の原因にも
  なり得るテーマで、「なぜ危険なのか」「どう書けば安全なのか」を
  理解していることは、実務で信頼される技術者になるための土台です。
- **cron連携**: サーバー運用では、「毎日深夜にバックアップを取る」
  「5分おきにヘルスチェックする」といった定期実行の仕組み(cron)が
  日常的に使われます。cronから起動されるスクリプトは、人間が
  画面を見ていない状態で動くため、対話的な入力を避ける・絶対パスを
  使う・結果をログとして残すといった、通常のスクリプトとは違う配慮が
  必要です。シバン行を使って「そのまま実行できるスクリプト」を
  作れることも、cron連携の第一歩です。

つまりこの章の内容は、**「Pythonを、サーバー運用の自動化ツールとして
使いこなす力」**の入り口です。ここが身につくと、監視スクリプトや
簡易的な自動化ツールを自分の手で書けるようになります。

## 3. 📖 解説

### 3.1 subprocess.run() の基本

`subprocess` は、Pythonの中から外部コマンド(Linuxのコマンドや、
他のプログラム)を実行するための標準ライブラリです。中心となるのが
`subprocess.run()` 関数です。

```python
import subprocess

result = subprocess.run(["echo", "hello"])
```

ポイントは、コマンドを **1つの文字列ではなく、文字列のリストとして
渡す** ことです。`["echo", "hello"]` は「`echo` というコマンドに、
`hello` という引数を1つ渡す」という意味になります。この書き方では
シェル(bashなど)を経由しないため、あとで説明する「シェルインジェクション」
の危険を避けられます。

`subprocess.run()` は `CompletedProcess` というオブジェクトを返します。
このオブジェクトから、実行結果に関するさまざまな情報を取り出せます。

### 3.2 capture_output / text / returncode

デフォルトのままだと、コマンドの出力は呼び出し元のターミナルに
そのまま表示されるだけで、Pythonのプログラムからは中身を読み取れません。
出力を「文字列として受け取りたい」ときは、次の2つのオプションを
指定します。

```python
result = subprocess.run(
    ["echo", "hello"],
    capture_output=True,  # 標準出力・標準エラー出力を受け取れるようにする
    text=True,             # 出力をバイト列(bytes)ではなく文字列(str)にする
)

print(result.returncode)  # 0 (終了コード。0なら正常終了)
print(result.stdout)      # "hello\n" (標準出力)
print(result.stderr)      # "" (標準エラー出力。今回は何も出ていない)
```

- **`capture_output=True`**: これを指定しないと `result.stdout` は
  `None` のままになります。
- **`text=True`**: これを指定しないと `result.stdout` は
  `b"hello\n"` のようなバイト列になり、`in` 演算子での文字列検索など
  文字列としての操作がそのままではできません(`text=True` を付けるのを
  忘れがちなので注意しましょう)。
- **`returncode`**: コマンドの終了コード(整数)です。Linuxコマンドの
  慣習として、**0は正常終了、0以外は何らかの異常・失敗**を表します。
  例えば `grep` は「該当する行が見つからなかった」場合に `1` を
  返しますし、コマンド自体が存在しない場合や致命的なエラーの場合は
  もっと大きな値になることもあります。「0かどうか」だけを見れば、
  多くの場面で「成功したか失敗したか」を判定できます。

失敗したら自動的に例外を発生させたい場合は `check=True` を指定します。

```python
subprocess.run(["false"], check=True)
# -> returncodeが0以外なので、subprocess.CalledProcessError が発生する
```

この章の演習では、`check=True` を使わずに `returncode` を自分の目で
確認して分岐する書き方を中心に扱います。「例外を待つ」のではなく
「戻り値を見て判断する」という考え方に慣れておくと、ヘルスチェックの
ような「失敗しても処理を続けたい」場面で役立ちます。

### 3.3 os.systemを使わない理由

Pythonには古くから `os.system()` という、文字列を渡すだけで
コマンドを実行できる関数があります。

```python
import os
os.system("echo hello")  # 動くことは動くが、この章では非推奨として扱う
```

一見便利ですが、次のような理由から、この章では **`os.system()` の
代わりに `subprocess.run()` を使う** ことを強く推奨します。

1. **出力を受け取りにくい**: `os.system()` は終了コードに近い値を
   返すだけで、標準出力を文字列として簡単に受け取る手段がありません。
2. **シェルインジェクションの危険がある**: `os.system()` は必ず
   シェル(bashなど)を経由してコマンドを実行します。もし実行する
   コマンド文字列の中に、外部から渡された値(ユーザー入力や設定ファイル、
   他のシステムから受け取ったデータなど)をそのまま埋め込んでしまうと、
   その値に `;` や `&&`、`|` のようなシェルの特殊記号が含まれていた
   場合、**意図しない別のコマンドまで実行されてしまう**危険があります。

   ```python
   # 危険な例(実行しないこと): filenameが外部由来の値だとすると…
   filename = "report.txt; rm -rf /important-data"
   os.system(f"cat {filename}")
   # -> "cat report.txt" のあとに "; rm -rf /important-data" まで
   #    実行されてしまう可能性がある
   ```

   これを「シェルインジェクション」と呼びます。SQLインジェクション
   (データベースへの命令文にユーザー入力をそのまま埋め込んでしまう
   脆弱性)と同じ発想の問題で、サーバーの世界では実際に発生してきた
   重大なセキュリティ事故のパターンの1つです。

   `subprocess.run(["cat", filename])` のように **リストで渡せば**、
   `filename` の中身がどんな文字列であっても「1つの引数」として
   そのまま渡されるだけで、シェルによる特殊記号の解釈は行われません。
   これが、コマンドをリストで渡すことが安全とされる理由です。

   (`subprocess.run()` にも `shell=True` というオプションがあり、これを
   使うと `os.system()` と同じようにシェル経由の実行になります。
   固定の・信頼できるコマンドだけを実行するなら使える場面もありますが、
   外部由来の値を埋め込む可能性がある場合は避けるべきです。)

3. **リスト形式の方が引数の扱いが正確**: スペースや特殊文字を含む
   引数(例: ファイル名に半角スペースが入っている場合)も、リストで
   渡せば「1つの引数」として正確に渡されます。文字列を組み立てる
   方式では、引数の区切りが崩れてしまうことがあります。

**まとめ: 外部コマンドを実行するときは、`os.system()` ではなく
`subprocess.run(コマンドと引数のリスト)` を使いましょう。**

### 3.4 シバン行(`#!/usr/bin/env python3`)

Pythonのスクリプトファイルの1行目に、次のような特別な1行を
書くことがあります。

```python
#!/usr/bin/env python3
```

これを **シバン行**(shebang line)と呼びます。`#` で始まるので
Python自身からはただのコメントとして扱われますが、Linux/macOSの
OSにとっては特別な意味を持ちます。「このファイルを実行するときは、
`/usr/bin/env python3` というプログラムを使ってください」という
指示です。

`env` を経由する書き方(`#!/usr/bin/env python3`)がよく使われるのは、
`python3` の実際の場所(`/usr/bin/python3` だったり
`/usr/local/bin/python3` だったりする)を気にせず、環境変数 `PATH`
から `python3` を探してもらえるため、環境が変わっても動きやすい
からです。

シバン行を書き、さらにファイルに **実行権限** を与える
(`chmod +x script.py`)と、次のように直接実行できるようになります。

```bash
chmod +x script.py
./script.py          # python3 script.py と書かなくても実行できる
```

サーバー運用の現場では、この「シバン行 + 実行権限」の組み合わせが
定番です。cronの設定ファイルや、他のシェルスクリプトから呼び出す際に、
`python3` を明示的に指定しなくてもスクリプト自身がPythonで実行される
ように書けるためです。

### 3.5 cronでの定期実行を見越したスクリプト設計

**cron** は、Linuxに標準で備わっている「決まった時刻・間隔で
コマンドやスクリプトを自動実行する仕組み」です。「毎日午前3時に
バックアップを取る」「5分おきにヘルスチェックを行う」といった
定期実行タスクの定番です。

cronから起動されるスクリプトは、人間がターミナルから手動で実行する
スクリプトとは違う前提で動くため、設計上いくつか気をつけるべき
ポイントがあります。

- **対話的な入力を避ける**: `input()` を使って人間の入力を待つような
  処理を書いてはいけません。cronは誰も画面を見ていない状態で
  スクリプトを起動するため、入力待ちのまま永遠に処理が止まってしまいます。
- **絶対パスを使う**: cronが実行時に使う環境変数(`PATH` など)は、
  普段ログインシェルで使っているものより少ないことが多く、
  相対パスやコマンド名だけでは「コマンドが見つからない」エラーに
  なることがあります。ファイルやコマンドは、できるだけ絶対パスで
  指定するのが安全です。
- **結果を記録に残す**: 定期実行されるスクリプトは、成功しても失敗しても
  「誰かがすぐに画面を見て気づく」ことは期待できません。第6章で学んだ
  `logging` と組み合わせてログファイルに記録を残したり、この章で
  学ぶ `returncode` を活用して「正常に終わったかどうか」を後から
  機械的にチェックできるようにしておくことが重要です。
- **returncodeで成功・失敗を表現する**: Pythonスクリプト自身も、
  `sys.exit(0)`(正常終了)や `sys.exit(1)`(異常終了)のように
  returncodeを意図的に設定しておくと、そのスクリプトを呼び出す
  さらに外側の仕組み(cronの通知機能や、監視ツール)が
  「成功したかどうか」を自動的に判定できるようになります。

この章の演習4で扱う「複数サービスのヘルスチェックレポート」は、
まさにこの考え方を使った、cronで定期実行されることを想定した
自動化スクリプトの典型例です。

## 4. 💻 サンプルコードの説明

`examples/example.py` には、この章で学んだ内容をまとめて動かせるサンプルコードが入っています。
以下のコマンドで実行できます(リポジトリのルートディレクトリで実行してください)。

```bash
cd /home/user/python
python3 modules/07_subprocess_jidouka/examples/example.py
```

サンプルコードは5つのセクションに分かれています。

1. **`section1_basic_subprocess_run()`**: `subprocess.run()` に
   コマンドをリストで渡し、`capture_output=True` と `text=True` を
   使って標準出力を文字列として受け取る、最も基本的な使い方を確認します。
2. **`section2_returncode_and_error_handling()`**: 正常終了するコマンドと
   異常終了するコマンドをそれぞれ実行し、`returncode` の値を見て
   成功・失敗を判定する方法、そして `check=True` を指定した場合に
   `CalledProcessError` という例外が発生する挙動を確認します。
3. **`section3_why_not_os_system()`**: `echo` コマンドだけを使った
   安全な実験として、「リストで渡す安全な書き方」と「文字列を組み立てて
   `shell=True` で実行する危険な書き方」を比較します。後者では、
   外部由来の値に含まれる `;` がコマンドの区切りとして解釈され、
   意図しない2つ目のコマンドまで実行されてしまう様子を、実害のない
   `echo` コマンドの範囲内で確認できます。
4. **`section4_shebang_and_executable_script()`**: シバン行
   (`#!/usr/bin/env python3`)を持つスクリプトを一時ディレクトリに
   実際に作成し、`os.chmod()` で実行権限を付与したうえで、
   `python3` を指定せずにファイルパスだけで実行できることを確認します。
   実行後は作成したファイル・ディレクトリを削除し、後片付けまで行います。
5. **`section5_cron_style_health_check()`**: 複数のサービスを模した
   コマンドをまとめて実行し、タイムスタンプ付きのヘルスチェック
   レポートを作成します。cronで定期実行されるヘルスチェックスクリプトの
   典型的な形を体験できます。あわせて、pingコマンドの出力を模した
   テキストを解析する例も確認します。

**外部ネットワークへのアクセスは一切行いません。** 実行するコマンドは
`echo` と `python3自身`(`sys.executable`)のみで、どのLinux環境でも
確実に動作します。シバン行のデモで作成する一時ファイルも、実行後に
プログラム自身が削除するため、リポジトリの中には何も残りません。
安心して何度でも実行してみてください。

### 演習3: `parse_ping_output(ping_output)` — 難易度: ★★☆

- **ファイル**: `exercises/exercise3.py`
- **目的**: 「コマンドの出力テキストを解析して意味のある情報を取り出す」
  という、監視スクリプトでよく使う処理の考え方を身につけます。
- **やること**: pingコマンドの標準出力を模したテキスト(文字列)を
  受け取り、その中に `"0% packet loss"` という文字列が含まれていれば
  `True`(到達可能)、含まれていなければ `False` を返す関数を
  実装します。**実際にpingコマンドを実行してはいけません。**
  与えられたテキストを解析するだけの関数です。
- **ヒント**:
  - `"0% packet loss" in ping_output` という書き方(第3章で学んだ
    `in` 演算子)だけで判定できます。
  - `in` 演算子はそのまま `bool` 値(`True`/`False`)を返すので、
    `if` 文を使わずに `return "0% packet loss" in ping_output` の
    ように1行で書くこともできます。

### 演習4(応用): `build_health_check_script_report(commands)` — 難易度: ★★★

- **ファイル**: `exercises/exercise4.py`
- **目的**: 演習1・演習2で学んだ「コマンドを実行してreturncodeを見る」
  考え方を、複数サービス分まとめて行う、実践的なヘルスチェック
  レポートの作成力を身につけます。
- **やること**: `commands` は `{サービス名の文字列: コマンドのリスト}`
  という辞書です(例: `{"web": ["echo", "ok"], "db": ["python3", "-c", "exit(1)"]}`)。
  各コマンドを実行し、`{サービス名: 成功したかどうか(bool)}` の辞書を
  返す関数を実装します。
- **ヒント**:
  - `commands.items()` で `(サービス名, コマンド)` の組を1つずつ
    取り出せます(第3章・第4章で学んだ辞書のループ処理の復習です)。
  - 各サービスについて演習1・演習2と同じように `subprocess.run()` を
    呼び出し、`returncode == 0` の結果を新しい辞書に詰めていきましょう。
  - 辞書内包表記
    `{name: subprocess.run(cmd, ...).returncode == 0 for name, cmd in commands.items()}`
    を使うと1行で書けますが、`for` ループと空の辞書を使う書き方でも

## 7. 🚀 発展課題

この章の内容に慣れてきたら、以下の発展課題にもチャレンジしてみましょう(提出は不要です)。

1. **標準エラー出力もあわせて返す**: `run_command` を改造し、
   `(returncode, stdout, stderr)` の3要素のタプルを返す
   `run_command_with_stderr` のような関数を作ってみましょう。
   `result.stderr` を使います。
2. **タイムアウト付きの実行**: `subprocess.run()` には `timeout` という
   引数があり、指定した秒数以内にコマンドが終わらない場合は
   `subprocess.TimeoutExpired` という例外を発生させることができます。
   `timeout=5` を指定して、時間のかかるコマンド(例:
   `["python3", "-c", "import time; time.sleep(10)"]`)を実行し、
   例外が発生する様子を第6章の `try/except` を使って確認してみましょう。
3. **ヘルスチェックレポートをログに残す**: 演習4の
   `build_health_check_script_report` の結果を、第6章で学んだ
   `logging` モジュールを使ってログファイルに書き出す関数を
   作ってみましょう。「異常があったサービスだけ `WARNING` レベルで
   記録する」といった工夫を加えると、より実践的になります。
4. **簡易的なリトライ機能**: 一時的な失敗を考慮して、コマンドが
   失敗した場合に一定回数まで再実行する `run_command_with_retry(command, max_retries)`
   のような関数を作ってみましょう(第6章の考え方の応用です)。
5. **`parse_ping_output` をより厳密にする**: 演習3の実装は
   `"0% packet loss"` という文字列が含まれているかを見るだけの単純な
   ものなので、実は `"100% packet loss"`(完全に到達不可能という意味)
   も部分文字列としては `"0% packet loss"` を含んでしまい、誤って
   「到達可能」と判定されてしまうという限界があります。`re` モジュール
   (正規表現)を使い、`"0% packet loss"` の直前が数字ではないことを
   確認する(例: `re.search(r"(?<!\d)0% packet loss", ping_output)`)など、
   より厳密な判定ロジックに改良してみましょう。単純な文字列一致には
   思わぬ落とし穴があることを体感できる、良い教材になるはずです。
6. **シバン行付きスクリプトをcrontabに登録する形を考えてみる**
   (実際に登録する必要はありません): `section4_shebang_and_executable_script`
   で作ったようなスクリプトを、「5分おきに実行する」という
   crontabの設定行(`*/5 * * * * /path/to/script.py`)としてどう書くか、
   絶対パスを使う必要がある理由とあわせてメモにまとめてみましょう。
